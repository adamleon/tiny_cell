# Decision Log

One entry per resolved design choice + the one-line *why*. Insurance against silently reversing a deliberate choice. When something seems odd, check here before "fixing" it.

---

**Candidate binding, not commitment.** Strategies propose a specific equipment model but as a candidate; the allocation layer (Layer 2) decides instance sharing. *Why:* committing to an instance inside the strategy makes cross-station equipment sharing impossible — two strategies would each spawn their own arm.

**Guards vs. preconditions are distinct.** Guards = unsolvable pass/fail predicates (reject immediately); preconditions = solvable sub-goals (spawn a child Task). *Why:* prevents the solver from trying to spawn equipment to fix unfixable geometry (e.g. an item that simply can't fit the pallet pattern).

**Capex on the catalog entry, not the strategy.** *Why:* same strategy + same model = same price regardless of task; storing it on the strategy duplicates and risks drift. Energy stays on the strategy because it depends on the task's required motion.

**Energy stored in joules, displayed in kWh.** *Why:* joules is an amount (composes cleanly, folds in duration); watts is a rate (can't cost without separately tracking time). kWh is the priced, human-legible unit — convert only at the cost/UI boundary. 1 kWh = 3.6 MJ.

**Standby power is a separate energy term.** *Why:* idle equipment still draws power; the `standby_power × idle_time` term penalizes underutilization, reinforcing the sharing objective.

**Strategies matched by capability (`applies_to`), not by task name.** *Why:* one strategy (e.g. a pusher) legitimately applies to multiple task kinds; name-wiring blocks that reuse.

**PusherStrategy models row-per-stroke palletizing, not box-per-stroke.** Equipment model the strategy assumes: items accumulate on an in-feed belt against an end stop until a full row is queued; the belt halts and the pusher transfers the whole row sideways onto the pallet in one stroke; the pallet belt then advances perpendicular by one box width to free space for the next row. The `evaluate` math falls out of this: `cycle_time = cycle_time_per_push × num_rows`; required stroke is the *smaller* pallet dim (the row direction; the larger dim is accumulated by belt advance); payload check is against the full row's combined mass (`item.mass × boxes_per_row`); `boxes_per_row = 0` (box too wide to fit a row) is a pattern infeasibility short-circuited before any catalog lookup. Concrete numbers and edge-case handling live in `solver/src/pusher_strategy.cpp` — that's the durable spec, not this entry. *Why:* the per-box model `PusherStrategy` first shipped didn't match real equipment — arm-style pick-and-place per item isn't how a pusher palletizes — and made pushers indistinguishable from arms in the OR-tree, hiding the equipment-class trade-off the enumerator exists to surface. Row-per-stroke is also what makes pushers genuinely competitive (an order of magnitude faster cycle on light/small-row tasks) and what makes them realistically *infeasible* on heavy or wide pallets (row payload sums, stroke can't cover the whole pallet). Aligns with `solver.md`'s worked example (PusherStrategy preconditions: `IndexPalletPosition`, `AlignItemOnBelt`).

**Item state = fixed small bundle, forward-propagated.** *Why:* a full predicate/effect planner is scope creep; a fixed bundle (position-known flag + Knowledge/Control axes on orientation + carrier placement) handles the real feasibility-gating cases for MVP. The name `ItemState` is honest: the struct bundles BOTH planner beliefs (pose precision via Knowledge) AND planner-tracked physical facts (carrier, Control) — see `data-model.md` §4.3. (Briefly renamed to `ItemKnowledge` mid-design when only the belief axis was tracked; the K/C split brought Control into the bundle and `ItemState` fits again.)

**Orientation modeled as symmetry-aware precision.** *Why:* you don't need a bottle's rotation; a square box only mod 90°. Reducing required precision by symmetry avoids over-speccing sensing equipment.

**Standards are data (rules file), enforced as hard constraints.** *Why:* expandable base set without code changes; compliance must not be traded off against cost.

**2D geometry for MVP, reachability-first then 30–70 % reach band.** *Why:* 3D + IK-in-the-loop is a different, much harder beast; 2D footprints + reach circles are tractable and sufficient for first layouts.

**Approximate optimum acceptable (LNS + simulated annealing).** *Why:* true global optimum on a mixed discrete-continuous (MINLP) problem is intractable at useful scale; the requirement explicitly allows "approximately optimal."

**Means-ends / regression-search planner not adopted.** Evaluated mid-step-3 (a proposal to recast the whole solver as backward search over a per-DOF constraint lattice, with equipment as typed precondition→effect transitions and an index keyed by `(DOF, Knowledge-or-Control, predicate)` driving Dijkstra/A*). One piece — the Knowledge/Control split on orientation — was adopted because it's a local refinement to the data model with concrete consumers (arm reads K, pusher reads C). The architectural reorientation around it was *not* adopted. *Why:* the project already commits to a different solver shape (Layer 1 OR-tree → Layer 2 allocation/packing → Layer 3 NLP placement → LNS outer loop) per `solver.md` and `roadmap.md`; means-ends regression is a different solver architecture, not a refinement of the existing one. The project also explicitly defers optimizer-library choice (this entry, above) — accepting the regression-search proposal would pre-commit to its index + search engine, undoing that deferral. The K/C split is a contained data-model improvement; replacing the solver paradigm is much bigger than the item-pose problem the proposal was framed against. Revisit only if step 4–6 evidence shows the Layer-1/2/3 + LNS shape genuinely doesn't scale on real workloads — at which point the change is "swap the optimizer," not "redesign the solver from the data model up."

**Lexicographic partial-handling (provisional).** Maximize fully-solved tasks, then minimize cost. *Why:* simple and matches "full solution prioritized over partial regardless of cost." Flagged provisional — can miss A-frees-resource-for-B cases.

**Graded interaction over single re-solve path.** A drag invalidates only the cheapest layer it breaks. *Why:* full re-solve per drag is far too slow for interactivity; tiered scope keeps free moves at frame rate and reserves full LNS for moves that genuinely change structure.

**SVG export of solver output is MVP-scope debug tooling.** A `svg/` top-level module emits 2D vector visualizations of any solver-layer output that carries geometry — catalog footprints + reach envelopes (step 1), station-local accumulated footprints (step 4), full `LayoutSolution` in world coords (steps 5-6). Pure C++ stdlib (no new dependencies); used by per-step demos and viable as a CI regression artifact (text → diff-friendly). Built incrementally per `roadmap.md` "Supporting tools", not a milestone in its own right. *Why:* the gap between when geometric solutions first exist (step 5, Layer 3) and when the threepp renderer / GUI arrive (post-MVP) covers the entire MVP-finalisation phase — without SVG, "did the solver place things sensibly?" is answered by reading JSON. SVG fills the gap cheaply and stays useful as a debug oracle even after threepp exists: different fidelity, different purpose. `svg/` is distinct from `render/` (threepp, post-MVP, interactive 3D, reads from the EnTT registry); SVG reads solver-internal structs + catalogs directly, has no foreign-lib dependencies, and emits text. They coexist after MVP — SVG for batch / CI / diff-friendly inspection, threepp for interactive editing.

## Architecture decisions

**`Strategy::evaluate` returns one `StrategyResult`, not `std::vector<StrategyResult>`.** *Why:* `data-model.md` §2 specifies a single result and the architecture answers the "compare multiple bindings" question through the OR-tree, not by fanning out from one call: each *strategy* contributes one proposal (its own internal best choice for that task), and alternatives (arm vs pusher; 1× big vs 3× small via PARTIAL chaining) come from *other* strategy proposals on the same task. The archive's experimental pattern (one strategy returns a vector of candidate bindings — e.g., `palletizer_options` over `(num_pickers, arm)`) is rejected here because it conflates strategy-class fan-out with intra-strategy parameter sweeps. Revisit if step 4's Layer 2 allocation needs visibility into trade-offs that neither strategy-class OR-fan-out nor PARTIAL chaining can surface — refactor single → vector is mechanical at that point.

**Item properties drive strategy gating, not item type.** Strategies must reason about item PROPERTIES (symmetry, dimensions, future surface/rigidity/chirality) via shared helpers — never switch on a discrete "what kind of shape is this" tag. *Why:* the alternative is nested if-trees on item type (`if (shape == Cylinder) … else if (shape == Square) …`) which every new shape forces every strategy to update. The property-based seam (`distinct_orientations(symmetry, knowledge)`, future `graspable_by(item, gripper)` / `stable_on(item, surface)`) localises change: adding a property is one helper + one strategy update per consumer, not a fan-out across every switch. The helper layer IS the architectural seam against type-switching. This pairs with the four-way concept split in `data-model.md` §4 (item-physical / item-knowledge / sensor-capability / actor-requirement+effect).

**ItemPhysical shared by composition; BoxSpec and PalletSpec remain distinct types.** Every item type (Box, Pallet, future Tote / Bottle / …) carries the same shape of physical fields (dimensions, mass, symmetry, growing later). These live on a single shared `ItemPhysical` struct that each spec type contains as a member — not by inheritance, not by aliasing. *Why:* (a) inheritance is out of style for pure-data domain types in this codebase (`decisions.md` "C++ class hierarchy with virtual dispatch rejected outright"); (b) aliasing the two would let `PalletizeParams { BoxSpec item; PalletSpec pallet; }` be silently constructed with the roles swapped at call sites; (c) wrapper-with-shared-struct gives a single locus for new physical properties (one struct touched, every item type picks them up) while preserving role-type-safety. Item-type-specific fields (Pallet stacking-pattern hints, future Box label class) live on the wrapper, not on `ItemPhysical`. Future `BoxInstance` / `PalletInstance` types will follow the same pattern: a wrapper containing an `ItemKnowledge` and a pointer to its spec.

**Variant-of-tagged-types for RotationalSymmetry and OrientationKnowledge; not magic-zero integer sentinels.** Each carries a `std::variant` of named arms (`Continuous | Discrete{period_deg} | Asymmetric`; `Unknown | Snapped{step_deg} | Exact`) constructed via validating factories (`symmetry::discrete(period)`, `orientation::snapped(step)` — both reject values outside `(0, 360)`). *Why:* (a) invariants by construction — there's no way to have a `period_deg` without committing to the `Discrete` arm, no way to construct a fold value outside the valid range; (b) avoids the cross-conventional confusion of "item granularity 0 = continuous" vs "knowledge granularity 0 = unknown" both being represented as the same int with opposite operational meanings — each variant arm names its own state; (c) helper functions like `distinct_orientations` dispatch cleanly via `std::holds_alternative` / `std::get_if` without needing sentinel checks. The cost is a small amount of variant ceremony at construction sites; the benefit is that "what state can this be in?" is enumerable in the type, not in convention.

**Orientation modelled as two independent axes — Knowledge and Control.** `ItemState.orientation` carries a `knowledge` field (planner belief, written by passive observation like a camera) AND a `control` field (physical constraint, written by mechanical actions like a fixture or side-guides). Strategy predicates read the axis their failure mode requires: arm-style strategies plan motion from the planner's belief and have end-effector compliance to absorb drift, so they read `knowledge`. Pusher-style strategies have open-loop strokes (no compensation once contact starts) and require the item to be PHYSICALLY held in the right alignment, so they read `control`. *Why:* a single "did we observe orientation?" axis is operationally wrong for pushers — a rectangle observed by a camera can still rotate on the belt before the pusher contacts it. Real cells solve this with in-feed side-guides / pre-fixturing that pin the alignment, and the predicate must check for that physical hold, not for the prior observation. The K/C split surfaces the distinction in the type system. Production pushers without a Control mechanism upstream are a latent failure mode the propagator now flags. Phase 1 carries single-alignment variants (`Known{alignment}` / `Constrained{alignment}`); a multi-alignment Hypotheses / Constrained-set form arrives in Phase 2 when a sensor with partial resolving power or a generous fixture lands.

**"Alignment" naming for symmetry-equivalence orientation classes.** The label for "which of the item's symmetry-distinct orientations the item is in" is **alignment**, not "class" (collides with the C++ keyword and with OOP-speak) and not "orientation index" (verbose and reads redundantly inside `OrientationKnowledge::Known{int orientation_index}`). *Why:* "two alignments for a rectangle" is exactly how the concept reads in plain factory language; the term is domain-native, generalises to other shapes (cylinder has 1 alignment, square has 1, hexagon has 2, asymmetric has 4 at the cardinal grid), and avoids the keyword/jargon collisions. Class index → alignment index is mechanical.

**Per-DOF position knowledge/control deferred to Phase 2.** Position stays as a single `bool position_known` in Phase 1. *Why:* no current strategy distinguishes "x known" from "y known." Arms and pushers both want both axes; cameras and fixtures both update both axes. The per-DOF generalization (`position_knowledge: { x, y }` + `position_control: { x, y }`) earns its complexity only when a single-axis sensor strategy lands (laser, encoder, edge probe). Until then it's pre-design without consumer. The orientation axis is already a per-DOF instance — θ with its own K/C pair — so the pattern is ready to replicate when position needs it.

**State-flow primitive (`requires_state` / `effect` on `StrategyResult`) is load-bearing; the batch walker (`propagate_state`) is a validator-only role.** *Why:* a live solver threads item state inline — state is *input to strategy selection at each task* (filter applicable strategies by `requires_state(state)`, then apply the winner's `effect` to produce the next state) — not something the solver builds a whole candidate and re-walks. So the pair of fields on `StrategyResult` is the reusable primitive every future state-aware consumer composes: a state-aware enumerator (step 4+), Layer 2 allocation candidate-check, LNS inner loop, and the eventual recovery-task spawning loop all read those two fields directly. `propagate_state` plays a different role: it takes a *finished* candidate from somewhere that didn't thread state and re-walks it to produce a Success-trajectory / Failure-at-index report. That role is real but narrower — it serves (a) late-stage validation of solutions imported, relaxed, or heuristically built; (b) the demo and tests for the step-3 layer; (c) a clean diagnostic surface for the user. It is NOT how the solver will consult state day-to-day. Keeping the batch walker for now because it is the layer's proof-of-life and its cost is low; revisit when step 4's state-aware consumer lands and tells us whether the validator role still has callers. If not, retire the walker and keep the primitive — the primitive is what matters.

**PARTIAL feasibility + precondition spawning staged to step 4, with the analytic throughput model.** *Why:* PARTIAL is the spec's mechanism (`data-model.md` §2) for "this strategy can serve some but not all of the task" — it returns `feasibility=PARTIAL` with `partial_info: { achievable_ct, target_ct }` and emits a residual `Task` in `preconditions` for the remaining work. This is how the OR-tree captures "1× big arm covers the task FULL" vs "3× small arms chained via PARTIAL" — *not* via multiple candidate bindings per `evaluate` call. The mechanism is only honest with a real throughput model (`achievable_ct` is not invent-able per `engineering.md` §3), and the throughput model is itself staged to step 4 along with cycle-time-as-hard-constraint. Step 1's `ArmStrategy` therefore returns only FULL or INFEASIBLE; the `PARTIAL` enumerator stays in `Feasibility` so the type doesn't change at step 4. Step 2's brute-force enumerator does not need PARTIAL — it validates strategy *matching* and *equipment selection* on tasks that fit FULL in a single binding.

**Strategies named `<EquipmentType>Strategy`, not `<EquipmentType><TaskKind>Strategy`.** *Why:* strategy-class reuse depends on one strategy applying to several task kinds (`ArmStrategy` covers `Palletize`, `Transport`, `Assemble`; `PusherStrategy` covers `Palletize`, `PushOff`). Naming a strategy after a single task forecloses that reuse and forces a combinatorial explosion of classes. Tasks must in turn be shaped equipment-agnostically (`Palletize(item, pallet, count)`, not `PalletizeWithArm`) — the OR-node fan-out in Layer 1 (`data-model.md` §2) only works if many strategies legitimately apply to one task. When tempted to name a strategy after a task, redesign the task or the strategy first.

**Per-category catalog loaders, not polymorphic dispatch.** *Why:* every consumer in the current design reads catalogs per category — strategies match tasks by capability and only consume their own category; asset files are already split per category (`assets/<type>/<vendor>/catalog.json`). A `std::variant<ArmSpec, GripperEntry, …>` (or class hierarchy) buys exhaustive-match safety only where a heterogeneous walk exists; we have none. Revisit when a consumer emerges that genuinely iterates over multiple categories in one pass — most likely candidate is `sync/` writing all equipment into the ECS registry (post-MVP, `architecture.md` §11). Refactor A→variant is mechanical at that point and we'll know which categories actually need to be in the variant. C++ class hierarchy with virtual dispatch (Option C) is rejected outright: equipment entries are pure data, behavior lives on strategies (`data-model.md` §2).

**Validated value types staged in at step 4 / Layer 2 allocation, not step 1.** *Why:* the wrapper layer (`PositiveLength`, `Payload`, `ReachRadius`, … — `architecture.md` §8) protects against *solver-produced* invalid values. In step 1 the only producer is the JSON loader, which validates at the `io/` boundary anyway; an extra wrapper layer is ~80 LOC enforcing nothing the loader doesn't already enforce. Step 4 (Layer 2 allocation) is the first point where solver code can violate a range invariant — that's when wrappers earn their cost. ArmSpec uses raw mp-units quantity types until then; promoting fields to wrapped value types is a mechanical per-field refactor when the time comes. (Reverses nothing in `architecture.md` §8 — that section describes the end state; this entry sequences when the layer is introduced.)

**Per-task throughput target — workflow-phase input; the solver consumes but does not allocate cycle time across stations.** The customer specifies a whole-cell rate (e.g. "100 pallets/h"); the *workflow phase* translates that into per-task throughput targets (e.g. "palletize task: 2400 items/h" at 24 items/pallet) and writes them onto each `Task`. The solver reads `target_throughput` as input and decides — via PARTIAL emission + the existing OR-tree fan-out — whether one instance covers it, multiple instances chain to cover it, or stations are replicated. *Why:* this resolves the open question flagged in `roadmap.md` "Cycle-time allocation" as gating Layer 2. The three candidate framings were even-split (wrong — stations differ in work content), bottleneck-driven (heuristic inside the solver), and solver-decided min-max balancing (turns allocation into a decision variable). All three put allocation logic *inside* the solver; the resolved framing moves it *out* — to the workflow translator that already knows the customer's units (pallets/h, parts/h) and the topology that converts them. The solver then only needs the PARTIAL mechanism already staged for step 4 (above): a strategy returning `achievable_ct_per_item > target_ct_per_item` is PARTIAL, residual throughput becomes a new Task in `preconditions`, and the OR-tree explores "1× big arm covers all" vs "3× small arms chained via PARTIAL" vs "replicate the station." No min-max balancer required.

**Throughput target stored as `time_per_item` on `Task` (not on `TaskParams`), `items/hour` reserved for the UI boundary.** Storage form is an mp-units `quantity_of<isq::time>` per item, named `target_ct_per_item` to match `achievable_ct_per_item` in `StrategyResult`. *Why (storage form):* feasibility is one direct comparison against `achievable_ct_per_item` — no unit conversion at the call site, no division in the inner loop. Mirrors the joules-vs-kWh decision above: canonical unit on the storage path, human-legible unit at the IO/UI boundary. *Why (on `Task`, not `TaskParams`):* every future task kind (Transport, Assemble, Inspect, …) carries a throughput requirement; placing the field inside `TaskParams` would duplicate it across every variant alternative. `params` carries goal-specific data (item, pallet, count); `target_ct_per_item` is task-level and kind-uniform. New-kind ergonomics stay clean — add an alternative, no throughput field to remember.

**Distance-based motion model — one seam, both cycle time and energy.** A free-function pair `cycle_time = f_motion(distance, payload, arm_spec)` and `energy_per_cycle = g_motion(distance, payload, arm_spec)`, called by `ArmStrategy::evaluate` (and any future kinematic strategy). Same `distance` argument drives both outputs. *Why:* for arms, both throughput (cycle time scales with motion length) and energy (active-power-time + standby) are coarse functions of pick→drop distance — the MVP cost objective wants energy as a function of distance to estimate lifetime cost, and cycle time has the same dependency for free. A unified seam means the throughput model and the energy model can't drift. At Layer 2 the `distance` argument is a placeholder (task-area envelope diameter, or reach diameter) since geometry isn't placed yet; at Layer 3 the placed pose supplies the real distance and the same call returns refined numbers. Future per-motion physics (accel/decel profiles, joint dynamics) replaces the function bodies, not the call sites. Coarse linear-in-distance is acceptable for MVP and explicitly endorsed in `roadmap.md` "Energy model granularity."

**Model-vs-reality safety margin deferred; framing recorded.** Two known sources of optimism in the step-4 throughput model: (1) *absolute* — the coarse motion model (straight-line at `max_speed`, ignoring accel ramps / path constraints / pick-place dwell) is structurally optimistic by roughly 1.5–2× for arms, so a "just meets target" solution in the model can miss in reality; (2) *comparative* — arm cycle time is *computed* from that optimistic model while pusher cycle time is *catalog-declared* (manufacturer-set with realistic test conditions baked in), so arm-vs-pusher ranking in the OR-tree skews toward arms even where pushers would actually win. Both mitigations are deferred — the right correction factors come from calibration against real-world data, not from architecture, and the motion-model seam (entry above) doesn't change when they land. *When implemented, the framing is:* (a) **overall safety margin lives on the *target*, not the motion model** — the workflow translator multiplies the customer's stated rate by a `realism_safety_factor` (≈1.3×) before writing `target_ct_per_item`, so strategies must beat a tighter spec than the customer demands. Keeps the motion model an honest physics estimate; matches industrial ~70 %-utilization sizing practice; symmetric across all strategies. (b) **Arm-specific derate addresses the comparison asymmetry** — a duty/efficiency factor inside `arm_motion_cycle` compensates for the structural gap, restoring fair arm-vs-pusher comparison. *Revisit when:* real-world calibration data becomes available, **or** the step-4 demo / a customer scenario produces a visibly-wrong strategy choice — whichever first.

**Pusher strategies emit only FULL or INFEASIBLE; refuse residual tasks.** PusherStrategy never returns PARTIAL, and `applies_to` returns false for tasks with `is_residual = true`. *Why:* a pusher physically owns its station — an in-feed belt indexing rows against an end-stop, a stroke direction, a pallet-advance perpendicular — none of which compose with a second pusher in the same station (two pushers ⇒ two stations). And a pusher cannot supplement another strategy as a "fills the gap" worker either: the alternative shape (e.g. "pusher pushes rows, arm stacks behind") is a geometric-residual model that's much more complex than the throughput-residual model PARTIAL is sized for, and it isn't standard industrial practice. Arms, by contrast, do compose — multiple arms in one station genuinely share work, and an arm CAN supplement a pusher (arm takes pusher's throughput residual). So the asymmetric rule: arms emit PARTIAL and accept residuals; pushers do neither. When a pusher's per-item cycle time exceeds the task's target_ct_per_item, the strategy returns INFEASIBLE rather than PARTIAL — the only way to add pusher capacity is replicating the station, which is a different mechanism (see entry below).

**Station-splitting mechanism deferred.** When no single strategy can return FULL for a task at the requested rate AND no PARTIAL chain converges (all eligible chainers exhaust), the eventual mechanism is *station replication*: split the rate target by N (N=2,3,4,…) and try the OR-tree with `target × N` per-station rate, each split becoming an independent station. The first N where every per-station target finds a FULL solution wins. *Why deferred:* this is a Layer-2 allocator concern (the strategies themselves don't see "stations"), and the allocator itself doesn't land until commit 7. The brute-force enumerator + tests in commit 9 can exercise PARTIAL chaining without station replication on toy problems where one-station solutions exist. *When implemented:* the allocator wraps the OR-tree exploration in an outer loop over N, treating INFEASIBLE-at-N as the signal to try N+1. Cost accounting sums across replicated stations as well as bound instances within each station.

**Energy model: three distinct power concepts; cost calc sums two without double-counting.** Three quantities that get conflated and are kept distinct in code: (i) `power_idle` from the catalog = the robot's always-on baseline (controller, fans, drives) drawn whenever the cell operates; (ii) `energy_per_cycle` from the motion model already integrates `peak × active_seconds + idle × idle_seconds` within one cycle, so within-cycle idle is baked into the per-cycle energy and is NOT a separate term; (iii) the data-model.md §6 `Σ_instances (standby × idle_time)` term applies only to BETWEEN-cycle gaps — when an instance is on but not cycling (demand < capacity). *Why this matters:* a naive read of data-model.md §6 plus the motion model would add idle power twice (once inside `energy_per_cycle` for the within-cycle dwell, once again as standby). The correct sum is `Σ_tasks (energy_per_cycle × cycles_per_lifetime) + Σ_instances (power_idle × gap_seconds_per_lifetime)`, where `gap_seconds = (1 - utilization) × op_seconds`. *The MVP physical simplification:* a real arm scaling down speed to "always in motion at minimum acceleration" would actually use less peak power and have no between-cycle gaps. Our model approximates this as "full-speed-with-gaps" — slightly overstates active energy, slightly understates idle baseline. Defensible for ranking purposes at MVP; real motion physics swaps in at step 5+ without changing the seam.

**Lifetime cost defaults from a KUKA 14-year survey (39 % capex / 27 % energy / 34 % maintenance+other).** The `LifetimeAssumptions` struct ships these defaults: `lifetime_years = 14`, `op_hours_per_year = 4000` (two shifts × 250 working days × 8 h), `electricity_eur_per_kwh = 0.22` (mid-range German industrial 2022-2024), `maintenance_other_ratio = 34 / (39 + 27) ≈ 0.515` (applied to capex + lifetime energy cost). *Why baked in:* the calibration data is real and would otherwise have to be rediscovered. Sanity check against KR 120 R3200 PA (88 000 EUR capex, 6 kW peak, 0.7 kW idle, 14 yr) at full utilization with these defaults lands within 10-30 % of the survey's 39/27/34 split, which is the right magnitude for MVP ranking decisions. The defaults are intentionally tunable — a workflow targeting 24/7 operation or a country with cheaper electricity will yield different splits and that's expected. *When to revisit:* if a customer scenario produces a visibly-wrong ranking decision, the right fix is changing assumptions (likely `op_hours_per_year` or `electricity_eur_per_kwh`), not the cost-calc shape.

**Hand-rolled allocator at Layer 2; library choice remains open for Layer 3.** Layer 2 (assignment + capacity-packing + reachability) is implemented as a hand-rolled greedy (first-fit capacity packing) behind an abstract `solve()` seam, no CP-SAT/IPOPT API leakage (`CLAUDE.md` §1). *(Status: the exact-on-small-N brute-force validator described in clause (b) is **planned but not yet built** — only the greedy ships on `dev`. `solver/src/allocator.cpp` is greedy `task_fits` first-fit; grep confirms no exact/validator path. Reconcile this before relying on a cross-check that isn't there.)* *Why:* (a) the previously-open optimizer-library decision (below) was deferred pending validation; Layer 2's regime is generalized assignment on a handful of tasks × a handful of instance candidates, exactly where library scaffolding cost outweighs algorithmic gain at MVP scale; (b) the step-2 brute-force enumerator is *intended to* extend into the exact-on-small-N validator — same test harness, broader scope, no new infrastructure (this cross-check is **not yet implemented**; it earns its keep once allocation gains enough freedom — instance sharing or station replication active in a real scenario — to make greedy-vs-exact divergence possible); (c) the abstract `solve()` seam means a future library swap (when scale demands it) is mechanical. **Library choice remains open for Layer 3** (continuous NLP placement) — the algorithm-vs-implementation cost ratio flips there, and IPOPT/SLSQP-on-Windows build pain is the real tiebreaker (`engineering.md` §2.3). Scoping the resolution to Layer 2 only.

**Layer-3 NLP backend: NLopt (SLSQP), via vcpkg.** Resolves the open question above for Layer 3. The PoC spike in `spike/layer3-optimizer/` confirmed NLopt installs and links cleanly on Windows via the vcpkg `nlopt` port — fresh (`nlopt 2.10.1#1`), ships a CMake config (`find_package(NLopt CONFIG)` → `NLopt::nlopt` target), single runtime DLL, and solves the spike NLP (min x²+y² s.t. x+y≥5) to the analytic optimum on first run. The vcpkg `coin-or-ipopt` port is **unusable on Windows out of the box**: ~84 min build pulling in MSYS2 + MinGW gfortran (the resulting `ipopt-3.dll` is MinGW-built, dragging four `libgfortran/libgcc_s_seh/libquadmath/libwinpthread` DLLs across an MSVC consumer's link surface), no CMake config (only pkg-config), and — fatally — no usable linear solver: all HSL variants (`ma27/57/77/86/97`) fail at runtime with `libhsl.dll not found` (HSL is closed-source, vcpkg cannot redistribute), MUMPS was not built into the port (`mumps` is not in the runtime's `linear_solver` valid-settings list), and `pardiso` requires a separately-licensed library. *Why NLopt is sufficient:* Layer 3 is a few dozen rigid bodies in 2D — well inside NLopt/SLSQP's scaling regime; NLopt also exposes alternate algorithms behind the same API (LD_MMA, LD_LBFGS, GN/GD globals) so swapping if SLSQP disappoints is a one-line change. *What's preserved:* the `solve()` seam stays library-agnostic per the Layer-2 entry above — a future move to IPOPT-built-from-source-with-MUMPS, Conan, or hand-rolled NLP remains mechanical. *Why this also resolves the dep-manager tiebreaker* (`engineering.md` §2.3): vcpkg passed for the only Layer-3 library we actually adopt; the OR-Tools/IPOPT-on-Windows risk that was the original reason to defer is moot once we're not using IPOPT. **Consequence:** this is the first time the main project takes a vcpkg dependency (everything else is FetchContent) — top-level `vcpkg.json` + `CMakePresets.json` toolchain wiring lands as a separate commit before any `solver/` code links nlopt. *See* `spike/layer3-optimizer/FINDINGS.md` for the full failure trace and what was not tested.

**Layer-3 algorithm: NLopt `LN_BOBYQA`, not `LD_SLSQP` (Phase E refinement of the entry above).** The Phase A spike validated SLSQP because the spike problem had an explicit inequality constraint that SLSQP handles natively. The actual Layer-3 objective has **no hard inequality constraints** — overlap and floor are encoded as smooth penalties — and those penalties carry C0 kinks at the `max(0, depth)²` boundaries where the gradient is discontinuous. SLSQP (gradient-based) can stumble on those kinks; BOBYQA (derivative-free, trust-region quadratic model) handles non-smoothness more gracefully. Plenty fast at MVP scale (a few stations). Switching to SLSQP or `LD_LBFGS` or `LN_COBYLA` is a one-enum change behind the seam plus, for derivative-required algorithms, finite-difference gradients in the callback. *Why this isn't a U-turn on the spike entry:* the hedge there ("NLopt also exposes alternate algorithms behind the same API … swapping is a one-line change") was deliberate exactly for this case — the *library* choice (NLopt) is the durable one; the *algorithm* enum is local. `solver/src/layout_problem.cpp` is the single site that changes.

**Floor as hard NLopt bound; overlap as soft penalty (Phase E discovery).** Per-station bounds `[floor.x_min + bounding_radius, floor.x_max - bounding_radius]` (and y) make the floor a hard constraint NLopt enforces directly; the floor penalty term stays in the objective as a safety net for the degenerate case where the bounding radius exceeds the floor extent (caught and rejected at `solve()` entry too). Overlap stays a soft penalty because pair-wise constraints don't fit per-variable bounds. *Why the split:* penalty methods converge to an equilibrium between competing terms — a soft floor penalty fighting the positional prior left ~mm of residual at the boundary, which the strict-zero `hard_constraints_satisfied` check rightly flagged as infeasible. Hard bounds eliminate that for the floor; overlap's residual is bounded by an explicit `1e-6 m²` engineering tolerance in the feasibility check (sub-mm penetration is below any real clearance). *When to revisit:* if overlap residual becomes load-bearing — e.g. for tight cell layouts or LNS feasibility certificates — convert overlap to an `LN_COBYLA` inequality constraint. The pair-wise constraint is one line per pair; the algorithm swap is the same enum change as above.

**Partial-freeze and warm-start expressed on `StationProblem`, not as separate API (Phase F).** Two mechanisms, one struct: `frozen=true` excludes a station from the NLP variable set (its pose is held at `initial_pose` while it still contributes to overlap penalties and feasibility checks); `initial_pose` IS the warm-start seed (first solves pass the positional-prior nominal, re-solves pass a previous solution's pose). *Why this shape:* both flows funnel through the existing `solve()` entry so callers don't need new entry points — LNS destroy-and-repair, future interactive editing, multi-stage solves all just toggle the flag and update `initial_pose`. The all-frozen case is a fast path: skip NLopt entirely (zero-dim opt rejects anyway) and return initial poses with the objective evaluated.

**Transport-distance term added to Layer-3 objective (step 6 Phase 1).** `LayoutProblem` gains a `transports` list of `TransportConstraint{source_station, source_port_local, sink_station, sink_port_local}`; `evaluate_objective` adds a quadratic `transport_penalty` term scaled by `ObjectiveWeights.transport`. The penalty composes each station pose with its port-local position to get port-world coordinates, then sums squared distance between connected port pairs. `AnchorStrategy` corrected to emit port_constraint in station frame `(0,0,0)` (anchor station is pinned at the world pose AnchorParams names; port at station origin recovers world via composition). *Why:* the placer previously had no incentive to move stations toward what they exchange items with — every layout looked the same as the prior. Closes step-5 deferral #2.

**Decomposed cost on `LayoutSolution` (step 6 Phase 2).** Replace `final_objective: double` with `cost: ObjectiveBreakdown { overlap, floor, prior, transport, total }`, all already weighted. `decompose_objective()` computes per-term values; `evaluate_objective()` wraps it returning `.total`. *Why:* downstream consumers (LNS trace, future GUI cost reporters, debugging) need to attribute cost changes to a specific term — a single scalar tells you nothing about *which* constraint is driving a move. Storage cost is four extra doubles per solution, evaluated once at solve() exit.

**MVP re-scoped (2026-05-27): inner-problem realism over outer-loop sophistication.** The original step 6 (LNS + simulated annealing) was implemented end-to-end and then evaluated: with single-station destroy + smooth 2D NLP inner solver, freed stations re-converge deterministically against the frozen rest, so SA never fires and LNS only polishes µm-scale numerical residuals on the convex sub-problems it generates. The audit revealed that the inner problem itself was the limiting factor (one-instance-per-station at origin, port positions at `(0,0)`, magical transports with no geometry, no realistic clearances) — an outer loop optimising over a toy inner produces a toy answer. *Decision:* move LNS, Layer-2 task sharing, and PARTIAL chain handling out of the MVP definition (none required for a single realistic palletizer cell); move port regions, belt geometry, intra-station packing (when needed), and realistic clearances *into* the MVP. The new "done" condition: produce a geometrically plausible layout for one real palletizing cell that a person could look at and recognise as such. The LNS scaffold is preserved on `feature/step-6-lns` (Phases 3-5) for when the inner problem becomes multi-modal enough to need it; Phases 1-2 (transport term + decomposed cost) cherry-picked to `dev` because the port-region work builds on them.

**Concrete-vs-abstract interpretation correction (2026-05-27).** The `concrete-over-abstract` rule means *dig deeper into the concrete*, not *defer the hard concrete thing because the abstraction isn't designed yet*. The MVP re-scope above was driven by realising I had been doing the inverse — using "no clear shape yet" as license to defer belts, intra-station packing, real port regions, and templated stations. The corrected interpretation: when tempted to defer a hard concrete thing because "the right interface is unclear," build the crudest concrete version that works for one real scenario and let the interface emerge. Two specific MVP additions from this correction: (a) `ArmStrategy` is expected to emit pallet ports as fixed Point regions in station frame (templated-ish inside the strategy, no new abstraction yet) rather than letting them be free annuli; (b) `validate_workflow()` lands in M3 instead of "deferred to GUI" — silent missing-edge failures are unactionable when evaluating whether the layout is real.

**Annulus reach-band enforced as a HARD polar (r, θ) box, not a soft penalty (step-6 M1.4).** When a transport endpoint is a reach-annulus port (`reach_max` set), the placer optimises its station-frame position as polar variables `(r, θ)`: `r` is hard-bounded to `[reach_min, reach_max]` (an exact 1-D box) and `θ` is free. *Why:* M1.3 shipped a soft `annulus_penalty` and the original M1.4 plan assumed it would be load-bearing with the box "just a sanity clamp." Adversarial review proved that false: a finite-weight soft penalty always loses to the (effectively unbounded) transport pull toward a distant sink, so at the default weights the port pinned to the cartesian box edge at ~2×reach — a physically impossible position reported as feasible (annulus is correctly a soft term, not in `hard_constraints_satisfied`). A cartesian box cannot express a radial annulus, and raising the penalty weight is fragile (the safe ratio depends on transport distance). Polar makes the radial band an *exact* box on `r` — weight-independent — and keeps the objective smooth in `(r, θ)`, so BOBYQA can swing the port around the ring; a kinky cartesian radial projection (tried first) stalled BOBYQA on exactly that swing. The soft `annulus_penalty` is kept as a redundant backstop (scores ~0 on the in-band port) and is still unit-tested as a pure function; `reach_min > reach_max` is rejected at `solve()` with a diagnostic, never clamped. Concrete impl: `port_local_from_polar` + the port-block bounds in `solver/src/layout_problem.cpp`. This reverses the original M1.4 plan, which specified the soft penalty as the load-bearing band mechanism. Polar's one degenerate point — `r = 0`, where `θ` has no gradient and BOBYQA cannot move — is avoided in the seeding: a port whose emitted seed is at the station origin (as `ArmStrategy`'s `item_in` is) is started at the band midpoint aimed at the other transport endpoint, not at `(r=0, θ=0)`. The M1.5 demo's real arm catalog surfaced this — its reach band is a disc (`reach_min = 0`), which the M1.4 unit tests (all `reach_min = 0.3 > 0`) had masked.

**Belt geometry: PlacedBelt sibling + post-solve sequential routing; BeltStrategy deferred (step-6 M2).** Transports become real placed conveyors via a POST-SOLVE routing pass, not an OR-tree change. `route_belts()` (`solver/belt_routing.{hpp,cpp}`) takes the resolved station poses + optimised port positions and, per transport edge, builds a `PlacedBelt` — a straight conveyor between the two resolved port world positions — selecting the cheapest `BeltSpec` (`core/model/belt.hpp`, loaded by `io::load_belt_catalog` from `assets/belt/generic/catalog.json`) whose `[min_length, max_length]` covers the routed distance, then flags belt-vs-station collision (convex separating-axis test against every non-endpoint station footprint; belt-vs-belt skipped). *Why post-solve and not a `BeltStrategy` in the OR-tree:* a belt's defining spec is its LENGTH, which depends on the PLACED source→sink distance — unknown at enumerate time, where arms/pushers are chosen from task params. And `TransferStrategy` (magic) returns FULL at zero cost, so a costed `BeltStrategy` competing in the OR-tree would always lose to free magic. So the OR-tree stays as-is (transports are connectivity, served by `TransferStrategy`) and belt geometry layers on top after placement — exactly what "transports become real placed objects with footprint and length" needs. `PlacedBelt` is a SIBLING type to `BoundInstance`, not a variant: a point-placed instance and a linear belt have different state (a belt has no single pose; its footprint is its route), so unifying them would force variant-handling everywhere. Collision is REPORTED, not repaired — feeding it back into placement is joint placement (one NLP over stations + belt routes), deferred until a real failure case appears; the cramped single-line `solve_workflow` demo already produces belt-vs-station collisions, but a 2D-spaced scenario (M3) is the proper test. `BeltStrategy` (the enumerate-level feasibility/cost competitor that would let belts replace magic transport) is deferred until belt cost/feasibility must drive selection — which means resolving the magic-transport disposition (the user's call; see "magic transport" steer).

**Realistic palletizer scenario: two-line robot plant + report-only workflow validation + in-code domain-credible clearances (step-6 M3).** M3 is the MVP go/no-go. Three decisions graduated:

- **`validate_workflow()` is a report-only topology pass in `solver/`, not a throwing parse check.** `solver/workflow_validation.{hpp,cpp}` exposes `validate_workflow(span<Task>) -> WorkflowValidation{ issues, ok() }`; each `WorkflowIssue` carries a severity + task id + message. Checks (the failure modes roadmap M3 names): duplicate task ids (Error), a Transport whose source and sink are the same task (Error — a self-loop is nonsensical and, uncaught, marks a task's own input as fed by its own output, masking a genuine unfed input), every Transport endpoint names an existing task (Error), source port exists + is OUTPUT / sink port exists + is INPUT (Error — the polarity rule in `port.hpp`), every INPUT logical port fed by ≥1 transport (Error — the canonical "`pallet_in` with no empty-pallet source" gap), every OUTPUT drained by ≥1 transport (Warning). The demo prints the issues and refuses to solve on any Error. *Why report-not-throw:* this is the `engineering.md` §3 "authored bad data" class, but workflows are C++ literals in demos at MVP (no io/ parse boundary yet), and the point is to *surface* missing edges actionably, not abort — so it returns a diagnostic list, never clamps or fabricates the missing edge. An io/-layer `ParseError` becomes its home if a JSON workflow loader lands. *Why solver/ not io/:* it reasons about workflow topology + `core::task_ports()` exactly as the solver consumes them; it is a pre-solve pass, not a file parse. *Severity split:* unfed input = Error (the cell cannot run), undrained output = Warning (product accumulates but the cell runs) — graded, not uniform.

- **Domain-credible clearances are a labelled per-category constant in the demo, NOT a standards JSON file.** `clearance_for(strategy_name)` returns ~0.5 m around arms / ~0.3 m for pushers, buffered into the station footprint via the existing `buffer_outward` pipeline (replaces the old uniform 0.2 m placeholder). *Why in-code and labelled, not data:* CLAUDE.md §5 forbids inventing *certified* numbers, and `standards.md`'s rules-file schema is an explicit draft. A labelled engineering placeholder in code is the honest signal that these are domain-credible-not-certified; promoting them to a `StandardRule` JSON file would over-formalise provisional numbers and pre-commit the draft schema. The magnitude (~500 mm robot safeguarding) lands now; certification and the data-file move are downstream, structure-free swaps.

- **The MVP scenario is a TWO-LINE robot plant; PusherStrategy is omitted and PARTIAL is avoided by construction.** `demos/solve_workflow` models one shared box feeder splitting to two palletizing cells — a heavy line (25 kg → KR30, payload-forced) and a light line (5 kg → KR6) — each with its own empty-pallet supply (also the anchors that pull the two arms into two rows) and a shared dispatch. *Why two distinct arms:* different payloads → different catalog ids → the allocator never collapses them (it only shares same-`catalog_id`), giving a genuine 2-station non-overlap/belt-routing problem (the HANDOFF's core "looks real" / 2D-spacing test the old collinear 3-task scenario failed). *Why generous per-box targets (8 s / 6 s):* they exceed every arm's achievable, so each cell is a clean single-arm FULL — no PARTIAL, hence none of the orphan-residual-arm artefact the old aggressive 2.0 s/2×2-pallet "tight" task produced (that orphan was correct PARTIAL-chaining, not a bug — diagnosed in M3). *Why omit PusherStrategy:* the scenario IS a robotic palletizing plant; arm-vs-pusher OR-tree competition is exercised in the brute_force / layer_2 demos. The strategy set is part of the scenario definition, so the omission is a scenario choice, not a solver change. Station θ stays fixed (objective is θ-independent), so the two-row spread comes from the north/south nominal seeds + the ±y empty-pallet anchors + overlap/clearance, not from rotating stations.

**Multi-equipment station footprint (M4.1): accumulated convex hull, templated layout, built caller-side via the adapter.** A palletizer station becomes a multi-equipment CELL — arm at the station origin + a real pallet-zone footprint (pallet size + working margin) at the templated `~0.6×reach` offset — and the station's collision footprint is the accumulated convex hull of its equipment (station frame), buffered by the governing (robot) clearance. *Why this is the M4 trigger:* roadmap M4 names "a pallet zone as separate equipment, not just a port at a fixed offset" as what turns the intra-station layout into a real sub-problem; M4.1 takes that first step (the pallet position now occupies floor the placer must reserve). *Why templated, not an NLP:* real palletizer cells are largely templated, so the intra-station layout is fixed offsets, not a free solve (roadmap M4) — the crudest concrete form. *Why built caller-side (demo) via the boost adapter, NOT a new solver module:* `solver/` depends on no foreign lib (CLAUDE.md §1) and `convex_hull`/`buffer_outward` live in the boost adapter, so the accumulated footprint is composed by the caller (the demo, which already buffers) from tested adapter primitives and passed to the placer as a plain `core::Polygon` — exactly how the demo already prepared single-equipment hulls. *Why hull-only (broad phase):* the lazy non-convex union packs elongated cells tighter than the hull's bounding circle allows, but it only earns its cost when a tight scenario forces it — in the current spacious two-row layout the footprint isn't even the binding constraint (transport+prior are), so narrow-phase is deferred. *What stays deferred to later M4 increments, NOT built now (anti-stray):* the lazy union + dirty-flag `StationFootprint` cache (data-model.md §3.1 — its world/local cache unification is itself an open design question), a free intra-station NLP, multi-instance stations, and promoting the hardcoded template to a `StationTemplate` type. Each lands when a concrete scenario needs it.

**Convex-polygon narrow-phase overlap (M4.2): SAT on the accumulated hulls, bounding circle kept as broad phase + fallback.** The inter-station overlap penalty gains a narrow phase: `overlap_penalty_poly(world_a, world_b)` returns the squared minimum-translation-distance between two convex footprint polygons via the separating-axis theorem (pure core — the same SAT family as M2's belt-vs-station collision, NO boost, so `solver/` stays foreign-lib-free per CLAUDE.md §1). `decompose_objective` / `hard_constraints_satisfied` flatten each station's accumulated hull to world ONCE per evaluation (the allowed one-transform-per-station flatten, not a per-pair `express()`), then per pair: bounding-circle broad-phase reject → polygon narrow-phase depth when both stations carry a footprint; a station with no footprint (anchors, radius-only test stations) falls back to the circle term. *Why:* the bounding circle is dominated by an elongated cell's longest extent (an arm + an offset pallet zone), so circle-vs-circle over-spaces stacked cells ~2× — M4.1 made the cells multi-equipment but the circle still set their spacing. SAT lets them pack to actual footprint contact. *Why the circle is KEPT, not replaced:* it is a correct, cheap broad-phase (hull ⊂ circle, so circles-clear ⟹ hulls-clear → skip SAT) AND the fallback that keeps the radius-only `overlap_penalty` API + all its existing unit tests intact (they construct stations with empty `buffered_hull` + a radius). *Why convex (hull), not the non-convex union:* the accumulated footprint is a convex hull, so SAT applies directly; nesting one cell into another's concavity needs the cell kept non-convex (the lazy union), which needs boost → caller-side → a later increment. *What the demo actually shows (verified by an adversarial review running the binary):* the two cells settle ~2.4 m apart, **just clear** of footprint contact — the solved overlap term is exactly 0 (a one-sided penalty is inactive on the clear side), and the demo prints a circle-vs-polygon diagnostic proving the payoff: a bounding-circle test would charge ~5.5 penalty at that spacing and demand the cells be ≥4.8 m apart (≈2× farther). So the narrow phase doesn't *push* the cells together — it *permits* the tight spacing the material flow already wants, which the conservative circle would have spuriously forbidden. *The stiff overlap weight (20000):* a softer weight let the cells settle a couple of mm INTO contact (the transport pull dragging them past the boundary), a residual the strict feasibility check rightly flagged — the stiff weight makes the penalty bite hard enough that they stop just clear instead. *Two reasons the principled fix is a hard `LN_COBYLA` inequality constraint, not a stiffer soft weight:* (1) the equilibrium residual just described; (2) deeper — SAT minimum-translation-distance is **non-monotone under deep penetration** (it peaks near coincidence then falls as one hull nests inside the other), so `sq(MTD)` is a valid repulsion potential only from a SEPARATED seed; a derivative-free descent seeded inside a neighbour could fall the wrong way. This is documented at `convex_penetration` and is the standing precondition the objective relies on (stations are seeded apart by the prior + floor bounds). Deferred per the "Floor as hard NLopt bound; overlap as soft penalty" entry, now with a concrete trigger.

**Catalog & workflow input format: JSON, not YAML.** *Why:* nlohmann/json is already part of the stack via the io/ parser, has stronger Windows/MSVC traction than yaml-cpp, and avoids adding a second text-config dependency. Authored bad data is still rejected with a typed `ParseError` at the `io/` boundary (`engineering.md` §3); the format choice is independent of the error mechanism.

**C++ throughout; interactive app from day one.** *Why:* EnTT + threepp + ImGui is a C++ GUI stack; OR-Tools and IPOPT are natively C++. No headless-CLI-first phase — interactivity is implied by the stack.

**Solver is a pure module on its own structs, syncs into the EnTT registry.** *Why:* LNS explores thousands of discarded candidates; mutating the live registry per candidate would thrash the renderer and couple search to ECS identity. The `sync/` step is the boundary.

**Frames have their own id space, not entity ids.** *Why:* the solver creates/discards candidate frames freely and may reference a frame before any entity is committed; one entity can both be-placed-in and define a frame (belt + its sensor). Coupling frames to `entt::entity` would drag the solver into ECS identity space.

**Frame-in-pose kept, but as FrameId.** *Why:* the original "pose carries its frame" instinct was right; the fix is the frame is a `FrameId`, never an entity id.

**Frame resolution composes transforms, not (x,y,θ) triplets.** *Why:* a parent's rotation rotates the child's offset; triplet addition silently mis-places rotated children (the rotated-belt/sensor bug).

**Geometry abstraction: abstract stored types, not algorithms; one adapter per foreign lib.** *Why:* makes Boost/glm/threepp swappable and core testable; foreign types leaking outside adapters would kill swappability. Convert at boundaries, never mid-kernel (performance).

**mp-units wired into the geometry types; units stripped only in adapters.** *Why:* compile-time dimensional safety (the joules-vs-watts class of bug); confining unit-stripping to adapters keeps stray unitless numbers out of core. Units and frames are orthogonal guards.

**Core/solver Z-up meters; Z-up↔Y-up confined to render adapter; handedness locked after confirming threepp.** *Why:* axis bugs are invisible until something renders mirrored; isolating the conversion to one file + a round-trip test contains them.

**Validated components via constrained value types, not public-field PODs.** *Why:* invalid geometry (length ≤ 0 etc.) produces silently-wrong layouts — the worst failure. Invariants pushed into value types (`PositiveLength`…) layered on mp-units, written once per concept; construction-time + immutable where possible; throw/assert never silent clamp; doesn't tax the solver because validation is at the sync boundary, not the LNS loop.

**Optimizer libraries (Layer 2/3) left open.** *Why:* they sit inside the solver and never touch core stored types, so the choice has no architectural cost; defer pending validation.

**Two-level lazy footprint flatten/cache (station-local, then world).** *Why:* intra-station and inter-station placement are independent problems; flattening at the station-footprint granularity means a station move is one polygon-transform, not a re-flatten of its equipment. World transforms touch only the moved station's single cached polygon. Keeps the LNS inner loop and interactive drag fast. Hull (broad-phase reject) + union (narrow-phase) cached together; clearance buffered in once at build time, never per collision check. Repair tries cheap inter-station nudge before expensive intra-station reorganization. See `solver.md`.
